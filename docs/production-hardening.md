# Production hardening

## Password pepper

Password hashes use Better-Auth's scrypt, sealed with AES-256-GCM under a key derived from `BETTER_AUTH_SECRET` with HKDF-SHA256. A database dump, backup, or read-only SQL injection no longer yields crackable hashes without the server secret. A full server compromise with that secret is outside this protection.

Stored format: `pw1:<16-hex key fingerprint>:<base64url(nonce || ciphertext || tag)>`. The fingerprint identifies the key without revealing it. The authenticated additional data (AAD) is `password-v1`. Better-Auth's password hooks receive no user id, so values are not bound to their row. A database writer can still swap two accounts' values.

The server seals legacy unsealed hashes and authenticates every sealed value at startup, in one transaction under an advisory lock, before listening. Sign-in never accepts unsealed hashes. Corrupt values produce a startup warning with a count and the recovery command; startup still succeeds when no unknown keys remain. `pnpm doctor:app` reports fingerprints, counts, and structurally invalid envelopes without changing data. It does not receive the key in its database probe; cryptographic authenticity is checked at server start.

To rotate the secret:

1. Stop every server/replica. Set `BETTER_AUTH_SECRET_PREVIOUS=<old>` and `BETTER_AUTH_SECRET=<new>` for EVERY server/replica at once, then restart them all. Both secrets must be strong, at least 32 characters, and different. Never run replicas with different `BETTER_AUTH_SECRET` configurations side by side: an old-config replica can neither verify re-wrapped hashes nor write current-key ones.
2. Check that the log `password pepper: re-wrapped … none remain under the previous key … BETTER_AUTH_SECRET_PREVIOUS can now be removed` or `pnpm doctor:app` shows 0 remaining under the previous key. Resolve doctor's invalid-envelope warnings before relying on its fingerprint inventory. If hashes remain, keep PREVIOUS set and restart all servers again. If they are corrupt, use the recovery command below.
3. Only after 0 remain, remove `BETTER_AUTH_SECRET_PREVIOUS` everywhere and restart all servers again.

Rotating `BETTER_AUTH_SECRET` still signs everyone out and makes existing TOTP enrolments undecryptable, as before. The previous key applies only to the password pepper; it does not preserve TOTP or purpose-derived credentials such as model API and CLI tokens.

A `PasswordPepperKeyError` refuses startup when stored values name an unconfigured key. Restore the secret used to write them, as `BETTER_AUTH_SECRET` or as `BETTER_AUTH_SECRET_PREVIOUS` during rotation. The message names fingerprints, never secrets.

If the key is lost, or values are corrupt or malformed, the owner stops all servers and runs recovery as a one-shot from a checkout with the validated server environment and database access. It needs no listening server:

```bash
pnpm auth:pepper:reset-unusable                     # dry run: count and affected user ids
pnpm auth:pepper:reset-unusable --confirm <count>   # exact count from the dry run
```

For production or any non-local database, add `--allow-non-local` to both commands, with all servers stopped. The command uses the same local database guard as maintenance scripts by default. It replaces only unusable password values with random passwords nobody knows, sealed under the current key. It keeps credential rows, legacy hashes, and authentic current/previous values. Start the server, then tell the listed users to use the normal forgot-password email flow. SMTP must be configured and working for that flow; configure SMTP before recovery if it was previously disabled.

**Backups:** `BETTER_AUTH_SECRET` also protects passwords. Back it up separately from the database and retain keys needed by older backups. A lost key requires the recovery procedure above for affected passwords. See [backup-and-restore.md](./backup-and-restore.md).

## Password recovery and in-flight authority

The Prisma adapter keeps Better Auth's default transactions off and makes only reset spends transactional. Verification mail is scheduled independently and reads the new user's locale through the shared client; an uncommitted sign-up row is not visible there. SMTP has bounded connection, greeting and socket waits plus retries, and does not belong in an interactive database transaction. Reset admission rechecks eligibility under the owner fence and commits token consumption, competing-link deletion, password and any mailbox proof together. A failed write rolls all of those back for retry; the independent pre-sweep remains committed and has revoked standing access. Queued database after-hooks run only after commit and after the spend's slot is released, including at pool size 3.

A mailed reset proves only the exact address recorded for that token and stages both `emailVerified` and `provedEmail` in the password transaction. With SMTP, a shown invite link leaves the mailbox unverified and unproved; it works only for a still-pending account carrying the permanent admin-invited marker. Without SMTP, a shown invite activates the account for sign-in without mailbox proof. Ordinary verify-email writes also serialize password-write before owner, invalidate competing reset links in their local transaction, and require one exact scalar, case-sensitive id or email selector for both update methods. Transaction-bound verification asserts the existing owner fence without reacquiring it after writes.

The reset after-hook accepts share invites only with SMTP and trusted committed `onPasswordReset` identity matching the current verified, proved address. It makes no token-based verification decision. Callback errors are deferred until that committed proof has been processed, then surfaced; rollback, missing callback evidence, changed identity/address and unproved mailboxes cannot accept shares. Both recovery revocation sweeps and the postcommit owner-fenced link cleanup remain in place.

Recovery sweeps run before the password write and again afterward, under the user's existing capacity `00:owner:<userId>` fence. They delete **all** owned sessions and sessions the user created by impersonation, pending two-factor challenges and their fence/OTP/counter rows, and trusted-device proofs. They revoke API keys, agent tokens, MCP grants, OAuth access/refresh tokens and consent, **node credentials and all unrevoked enrollment codes**, including partly used multi-use codes. Nodes and their configuration remain intact. Reconnect an existing node using a fresh **Replace** enrollment code; use a fresh enrollment code for a new node. After each committed recovery sweep the server's machine-credential listener closes that user's relay sockets promptly; the existing ban notification also cancels browser work. Notifications are process-local, matching the documented single-web-service deployment; another replica would still refuse revoked credentials on its next authoritative check.

A successful password change with `revokeOtherSessions: true` keeps only the session token returned by that change and revokes other sessions/standing credentials. It preserves node credentials and enrollment codes. A change that keeps other sessions does not request a credential sweep.

Email/password sign-in fingerprints the stored credential before Better Auth verifies it, checks before session creation and rechecks after insertion. A changed credential refuses the session and removes any new rows, with no session cookie. Two-factor password steps store the same fingerprint beside their challenge, and code steps require it to match before and after insertion. Every session derived from a signed-in request (including two-factor rotation and impersonation) needs its parent session row before and after insertion; a failed after-check deletes the new row. Session renewal updates the existing row and cannot resurrect a deleted one.

Only exact `POST /api/auth/admin/stop-impersonating` checks the original actor rather than the current target. It requires a live impersonated target session and exactly one unquoted, signed saved-admin cookie naming an existing, unexpired, non-impersonated session owned by that target session's `impersonatedBy`. The saved actor is loaded fresh and must satisfy verified-admin, forced-2FA, ban and pending-deletion rules. The target's role and lifecycle cannot authorize or veto the return. Every other admin path and method keeps the strict active-admin gate and the existing oRPC-only access-change restrictions. Better Auth receives the original request and retains its origin/CSRF, expected-identity and restoration handling.

The pinned Better Auth 1.7.18 session-creation inventory is:

Enabled plugins are admin, twoFactor and (when MCP is enabled) JWT, MCP's OAuth provider, and CIMD. The JWT/MCP/OAuth-provider/CIMD implementation has no additional browser `createSession` call. Device authorization, username, magic link, email OTP sign-in, passkeys, phone, anonymous and other sign-in plugins are not enabled. Unknown paths and server-only session creates without a parent fail closed. New-user password-account creation is exempt only for `/sign-up/email` and `/admin/create-user` under this app's server-only invite locale grant. Every other password-bearing account create/update, including a server-only set-password call, requires the password-write lock.

`handlePasswordAuthRequest` is mounted in `apps/server/src/app.ts` after the existing IP/rate/verified-admin gates. It wraps POST `/change-password`, `/reset-password` and `/admin/set-user-password` in a standalone per-user password-write lock, and POST `/sign-in/email` in the credential fence. A change waiting behind recovery rechecks its session inside the lock and answers 401 without writing; recovery waiting behind a change writes last. Lock/slot waits share one 10-second deadline (503 `PASSWORD_WRITE_BUSY`). The 30-second transaction's held flag lapses five seconds early. Account after-hooks probe the still-open transaction after the independent password write commits. An unconfirmed write is quarantined: random unusable password hash, all sessions/challenges/standing/machine credentials revoked, 409 `PASSWORD_WRITE_UNCONFIRMED`. Recover using Forgot password.

There is no direct admin password-reset UI: the pending-account dialog remains an invite/resend flow. The default admin plugin's direct `/admin/set-user-password` recovery API remains reachable through the existing verified-admin/forced-2FA gate. Its password-bearing account hooks run **after** Better Auth's endpoint authorization and perform both recovery sweeps under the password lock. A generic endpoint before-hook never revokes on this path. Bulk account after-hooks receive a count, so request-local evidence from the authorized before-hook identifies the post-sweep. Direct server calls outside the lock fail closed. No admin/impersonation capability was broadened.

### Lock order and pool accounting

The order is **password-write → capacity owner fence → setup work**. Credential revocation/minting and credential setup use the **same** owner fence; there is exactly one per-user setup fence, not another advisory mutex. Every capacity transaction acquires its sorted fences before a row lock/write; it cannot acquire a new fence afterward. No owner-fence holder waits for an outer password-write lock. Quarantine never takes that outer lock again. The static advisory-site and graph-writer census in `apps/server/src/model-api/capacity/lock-order.test.ts` includes the standalone password lock and pins its acquisition before the handler.

`packages/db/src/lock-slots.ts` is the only slot accounting implementation; auth re-exports it. The actual request `PrismaPg` pool consumes validated `DATABASE_POOL_MAX` (default 10, minimum 3) through `maxConnections`. At most pool-max minus one transactions hold/wait for locks. A password write reserves its own slot and one nested slot before checkout, leaving a connection for Better Auth's independent writes. `runCapacityOrderedTransaction` prepays a slot, and the shared client's transaction boundary consumes that ticket once; raw transactions allocate their own slot **before** checkout. It rechecks the shutdown fence after a slot wait and preserves the release guard. Startup configures accounting beside actual pool construction, avoiding an eager environment-validator dependency for pure capacity helpers. Concurrent children compete FIFO for their live parent’s reserved spares; they wait in memory until a borrower returns them. A nested request that cannot fit its parent’s reservation fails before checkout. When a holder exits, descendant reservations and unused tickets expire, and queued children move to the global FIFO with their original deadlines. Active borrowers keep their slots charged until they actually finish, even if their parent has already exited.

Central lock audit:

- Capacity transactions, including graph writes, MCP grant issuance/redemption/rechecks, standing credential mints/revocation, node exchange and enrollment-code issuance: accounted by `runCapacityOrderedTransaction`. Existing standing-credential mints recheck their browser/authorizing session under the owner fence. Exchange uses its enrollment code as proof, rechecking that code under the same owner fence; it never requires a browser session.
- Raw `password-reset-links.ts` mail marks and preliminary eligibility cleanup; `password-reset.ts` postcommit link cleanup; `account-activation.ts` activation cleanup; API `set-password-link.ts` mint/mark transactions: accounted by the shared-client transaction boundary, using the existing owner fence. None waits for password-write.
- `credential-setup-adapter.ts` selective reset transactions borrow the password holder's reserved slot. Standalone verification reserves a slot before checkout, then acquires password-write and the owner fence on that same client. Reset consumption takes the owner fence once before writes; a later bound verification write uses the read-only owner-fence assertion.
- `password-pepper-store.ts` startup conversion and owner-run offline recovery: shared-client slots, one standalone pepper lock first, no later owner fence. The recovery command runs with servers stopped. No change to its lock or offline authority policy.
- The password-write transaction: one slot plus its reserved nested owner/setup transaction. The sign-in fingerprint fence uses no transaction/slot.

Invite and resend procedures charge a bounded process-memory budget before account/token writes or mail: `rl:users-invite-mail` allows 30/hour per admin shared across both procedures; `rl:users-resend-invite` allows 5/hour per target across admins. Exhaustion/unavailable clock/memory capacity fails closed with the existing API error contract. Expired entries are removed, keys are fixed-size digests and at most 10,000 entries are retained. Restarting the single service resets this delivery budget; it is not a distributed rate limiter.

Cookie caching remains disabled here, so there is no configured cookie-cache read window. If enabled later, cached reads could last its `maxAge`, but parent/mint checks still require a live row. A raced two-factor disable can change the flag but receives no session; sign in again and re-enroll. An old-password sign-in that commits before the reset hash may briefly mint access; the post-sweep removes it. Exhausted post-sweep database failures log `SECURITY` and propagate, requiring recovery/manual revocation; they are not reported as successful security completion. No system can undo work already completed before recovery, or secure a fully compromised server.
