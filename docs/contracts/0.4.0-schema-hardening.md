# 0.4.0 schema hardening plan (keep / drop / add)

Contract for chunk S0a and the chunks that own each table. Source of truth for the tables is
`packages/db/prisma/schema/*.prisma` (fresh 0.4.0 baseline). This file classifies **every named
object** in the current `packages/db/prisma/schema-hardening.sql` (205 objects: 58 constraints,
56 functions, 69 triggers, 22 indexes) and lists what 0.4.0 adds. Spec: §2.13 and §2.14 of
`claude-0.4.0-spec.md`.

## Layout

- **Decision (S0a): one file, one section per domain.** `schema-hardening.sql` keeps its single
  file and transaction, with sections in the order of the Prisma files (shared helpers, auth,
  nodes, runtimes, profiles, pools, access, providers, telemetry, misc, the generated registry
  block, then the fences). Splitting it into files would only add a concatenation step to the
  deploy path (`apply-schema-hardening.mjs`, the Dockerfile COPY list and the version gate) for
  no runtime benefit; the sections keep the per-domain ownership readable. The hot-path tables
  (`hotpath.sql` below) get their section with the S0d engine rekey.
- The registry CHECKs (`pool_advanced_overrides_check`, `runtime_version_advanced_check`,
  `runtime_version_limits_check`) are generated by `packages/db/scripts/registry-checks.mjs` from
  `pool-defaults.ts` / `runtime-defaults.ts`; the verifier fails when the block is stale.
- Every backfill in the current file is dropped (fresh baseline, no data migration).
- `verify-schema-hardening.mjs` keeps its role (source checks plus the PostgreSQL integration
  run behind `SCHEMA_VALIDATION_DATABASE_URL`). Each object below lands **with its verifier cases in
  the chunk that owns its table** (column "Chunk"). F1 is only a final audit.
- Prisma now declares every FK the SQL used to add by hand. The SQL never re-adds an FK Prisma
  owns.

Legend: **K** keep (same logic), **K→name** keep and rename, **R** keep the purpose with a
rewritten body, **D** drop.

## Delete rules (verifier cases, chunk S0a; behavior chunk A4)

FKs on paths that also cascade from elsewhere are `NoAction` in the Prisma schema
(instance → runtime/version/launch version, `Runtime.currentVersion`, profile item → version,
pricing version → model/account, `ProviderCredential.ReplacedBy`). The deletion sweeper deletes in
a fixed order: instances → profiles → runtimes (current version nulled first) → nodes → pools →
providers → user. Verifier cases:

1. delete a user with running always-on and multi-node instances;
2. delete a node holding the head and a worker of a multi-node instance;
3. delete a node holding only a worker;
4. delete a runtime pinned by a profile (refused by the `NoAction` FK, mapped to `pinned_by_profile`);
5. delete a pool used as another pool's sidecar;
6. delete a share with contributed members.

## Decisions taken while classifying (beyond spec §2.13)

- Hot path (S0d section of the SQL): the waiter policy snapshot follows the limits redesign with
  the 0.4.0 pool shape. A pool candidate carries the pool's class (or the share's class recorded
  on the request), the pool cap as its only scope (`POOL`, no member caps any more), kept slots
  and borrowing from `pool_routing`; a contributed member runs BACKGROUND, keeps nothing and may
  borrow. A TEST candidate (direct served-model test, D1) runs NORMAL with no scope limit, no kept
  slots, and may borrow: direct targets carry no policy. The cache-affinity generation is the
  instance's `cacheGeneration` plus the head node's connection generation (the always-on
  runtime's node, or rank 0's).

- `pool_routing_rule_memberId_fkey`, `provider_budget_settlement_reservation_revision_unique` and
  `provider_usage_ledger_attempt_revision_unique` are dropped: Prisma now declares the same FK /
  unique, so the SQL copies would be duplicates.
- `relay_request_execution_target_consistency` is listed under "drop" in spec §2.13 only as a
  trigger of the dropped consumer function; it comes back as its own small check in
  `telemetry.sql`, because §2.13 "keep" also names it.
- No separate partial unique for contributed members (first review §5): the Prisma
  `@@unique([poolId, runtimeModelId])` already allows one member per model per pool, contributed
  or not.
- `deployment_instance_node_held_unknown_id` is kept (as `instance_rank_held_unknown_check`)
  because the held-unknown probe sweep (§3.5) scans exactly those rows, least recently checked
  (`lastStopCheckAt`) first, so more ranks than one pass takes are all reached.
